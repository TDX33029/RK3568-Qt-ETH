# RK3568 定位系统 故障排查总结

> 整理时间：2026-08-11
> 涉及项目：
> - `260806-impl/spi-old/`（RK3568 端 Qt 定位 UI 源码）
> - `FW/`（STM32F407ZGT6 仿真传感器固件）
> - `Host/`（PC Python 上位机）
>
> 三者通过两条独立链路连接：
> ```
> PC上位机 ──UART(USART1)──► F407 仿真器 ──SPI2从机──► RK3568(主机) ──► Qt EKF UI
> ```
> 关键点：**PC 上位机与 RK3568 是两条互不相通的链路**。PC 上发命令只作用于 F407，对 RK 端无任何影响。

---

## 一、问题清单

| # | 现象 | 严重度 |
|---|------|--------|
| 1 | PC 上位机下发仿真命令后，RK3568 板子"没有任何动作" | 中（认知问题） |
| 2 | 程序启动收到数据后，所有终端打开都不显示 | 高 |
| 3 | 关闭开发板重新上电后，板子无法启动（实际为 HDMI 黑屏） | 高（误判为变砖） |
| 4 | 串口持续刷 `dw_hdmi ... failed to set CONNECTOR_ID` / `broken atomic modeset` | 中（干扰） |
| 5 | 用户希望"恢复到之前有图形界面"并查清卡死原因 | 目标 |

---

## 二、诊断过程与结论

### 2.1 RK3568 端 SPI 链路本身是正常的

用户提供的 F407 STATUS 日志：
```
STATUS seq=0 运行=1 帧=328357 SPI读=138784 CRC=0
```
- `running=1`：F407 仿真在跑（上电即 `s_running=1`，见 `FW/User/app/app.c:280-283`）。
- `frame_count=328357`：TIM2 在持续 `SIM_Step`。
- **`spi_xfer=138784`**：DMA 传输完成中断计数，证明 **RK3568 一直在成功读取 182 字节 SPI 帧**（只有主机读走数据、DMA TC 中断触发才会累加，`FW/User/bsp/bsp_spi.c:129`）。
- `CRC=0`：帧全部合法。

**结论**：F407 仿真、SPI 物理链路、RK 端读取均正常。问题不在硬件、接线、上电时序。

### 2.2 "RK 没有动作"的真正原因

RK 端 `SpiReader` 只在 `MainWindow::startLive()` 被调用后才会 `open(spidev)` 并启动线程（`mainwindow.cpp:332-355`）。用户确认**已点击 `Start Live (SPI)` 按钮**。结合 2.1 可知：SPI 数据在持续被某进程读取，但用户看不到 UI 更新——根因是**显示层卡死**（见 2.4），而非数据没来。

> 认知误区澄清：PC 上位机的"下发配置 / Start / Stop"命令只到 F407，**不会、也无法驱动 RK 端 UI**。RK 要动必须在其自身界面点 `Start Live (SPI)`。

### 2.3 串口日志的性质

`log.txt` 与实时串口输出均为**正常内核启动 dmesg**，反复出现三类无害告警：
- `GTP-ERROR ... I2C Read failed`：触摸屏没接。
- `rk_gmac ... Failed to reset the dma`：网口未插网线/未初始化。
- `dw_hdmi ... failed to set CONNECTOR_ID` + `broken atomic modeset`：**HDMI 显示属性设置失败，内核 DRM 驱动循环重试**。

**无任何内核 panic / Oops / 死机字样**，内核能跑到 240s+，证明硬件未损坏、系统未崩溃。

### 2.4 "系统卡死 / 终端不显示 / 黑屏" 的真实机制

因果链：
1. **HDMI/DRM 显示栈在固件层面本就脆弱**：内核不断刷 `failed to set CONNECTOR_ID` 并 `disabling atomic`，这是板子驱动/屏兼容的固有问题（与用户程序无关）。
2. **Qt 程序默认使用 wayland/eglfs 平台插件**（`qt_add_executable` 在 RK Qt 环境下默认选择），该插件需与 Weston/DRM 原子提交交互。
3. **两者叠加 → 显示会话挂死**：程序不断向半坏的显示栈做 atomic modeset，每次被内核拒绝 → 陷入重试循环、显示资源被锁死。结果：**整个显示子系统卡住，所有 GUI 窗口（含新开终端、HDMI 画面）不再刷新/显示**。
4. **"重新上电黑屏"**：上电自启 Weston → Weston 同样碰坏的 HDMI/atomic 路径 → 桌面卡死 → 表现为黑屏。这是"起来了但显示挂了"，**不是启动失败、不是变砖**。

**关键证据**：用户通过调试串口（MobaXterm）成功拿到 shell 并执行命令（返回 DONE），证明内核与系统完全存活，仅"画面层"死透。

### 2.5 Weston 状态确认

用户执行 `ps aux | grep -i weston` 仅剩 grep 自身；`systemctl disable weston` 后，内核级 `irq/40-dw-hdmi-`、`cec-dw_hdmi` 线程仍在（内核线程无法 kill），串口刷屏持续。证明刷屏来自**内核 DRM 驱动自身循环**，非用户态进程。

## 三、已执行的拯救操作（有效）

1. 通过 **USB-TTL 调试串口（UART0, 波特率 1500000）+ MobaXterm** 进入 shell（HDMI 黑屏不影响串口）。
2. 杀掉卡住的显示进程：
   ```bash
   killall -9 ps_tracker_ui 2>/dev/null
   killall -9 weston 2>/dev/null
   systemctl stop weston 2>/dev/null
   systemctl disable weston 2>/dev/null
   ```
   均返回 DONE，shell 可用，板子可控。

## 四、待解决 / 下一步方案

### 4.1 恢复图形界面（用户诉求）

需先确认 HDMI 是否还能出画面：
```bash
systemctl enable weston 2>/dev/null
systemctl start weston 2>/dev/null
sleep 3
ps aux | grep -i weston | grep -v grep
```
- **A：Weston 起且 HDMI 出画面** → 之前是被 kill 导致，恢复桌面即可，再按 4.2 正确启动程序。
- **B：Weston 起但 HDMI 仍黑** → HDMI 显示通路确已损坏（内核级报错），当前屏上无法恢复图形，需换兼容屏/线或改设备树。
- **C：Weston 起不来/再卡死** → 走 offscreen 路线（4.3）。

### 4.2 程序启动必须避免再卡死（治本）

**绝不裸跑 `./ps_tracker_ui`**。必须指定平台插件绕过脆弱的 Weston/atomic：
```bash
./ps_tracker_ui -platform linuxfb      # 直接写 framebuffer，最稳
./ps_tracker_ui -platform offscreen    # 仅验证逻辑，不画图
```
程序位置需先 `find / -name "ps_tracker_ui" 2>/dev/null` 定位（当前在 `/root` 下找不到）。

### 4.3 若 HDMI 确已不可用：offscreen + 串口看数据

给 `mainwindow.cpp` 增加：
- `-auto-live` 参数：启动即自动调用 `startLive()`，无需点击按钮（offscreen 下无法点）。
- 每帧将 `seq / dt / 估计位置 / 收帧数` 打到 stdout（串口可见）。

### 4.4 代码层潜在优化（避免高占用拖垮系统）

`spi_reader.cpp:83` 轮询周期写死 10ms（`mainwindow.cpp:354` `setPollPeriodMs(10)`）。RK3568 小核上，每帧 = spidev ioctl 全双工 182B + CRC 校验 + EKF 更新（逐观测 Joseph 形式，单目标 5 锚点 × 4 模态约 20 次矩阵运算），耗时可能逼近/超过 10ms，长期占满 CPU 叠加显示问题会加剧卡顿。建议放宽到 **20~33ms**（30~50Hz 对定位足够）。

## 五、关键认知总结

1. **板子没坏、系统没崩**：黑屏 = 显示层挂死，内核与 shell 存活（串口可证）。
2. **HDMI 黑屏是固件/驱动/屏兼容的既有问题**，非用户程序造成；内核级报错无法用 kill 消除。
3. **PC 上位机命令到不了 RK**：两条独立链路，RK 动必须在其自身 UI 点 `Start Live (SPI)`。
4. **程序必须用 `-platform linuxfb` 启动**，否则默认 wayland/eglfs 会再拖死显示。
5. **救板入口是调试串口（UART0, 1.5M 波特）**，不是 HDMI、不是 SSH（网口未起时连不上）。
6. 当前状态下**不要反复上下电、不要裸跑程序**，shell 已可控，按 4.1~4.3 推进即可。
