# 5.4 交互界面与 PS 端算法移植显示系统实现

为避免三维定位跟踪算法的验证过程长期依赖 MATLAB 在线运行环境，本文将单目标定位跟踪算法进一步移植到 Zynq/AC820 开发板的 PS 端，在 Linux 用户态下采用 C 语言完成算法执行、结果统计和图形显示。这样一来，实验不再依赖上位机实时参与，开发板本身即可完成参数配置、目标轨迹仿真、测量生成、状态估计、误差计算以及 LCD 结果显示，形成“本地配置、本地运行、本地显示”的完整实验闭环。对于第五章而言，这一部分的意义不仅在于实现一个交互界面，更重要的是证明前述定位跟踪算法已经能够脱离 MATLAB 环境，在嵌入式平台上独立稳定运行。

结合本课题的实际开发流程，PS 端系统并不是直接在开发板上本地编译生成，而是先在 Windows 主机端完成 ARM 交叉编译，再将生成的可执行文件复制到开发板上运行。随后，开发板在 Linux 用户态下完成算法调用、结果统计和 LCD 显示。因此，本节不仅讨论界面绘制方法，还完整说明“PC 端编译、板端部署、PS 端运行、LCD 端显示”这一整条实现链路。

本节所实现的板端程序典型运行入口如下：

```bash
cd /media/sd-mmcblk0p1
./fb_tracker_ui
```

## 5.4.1 设计目标与总体思路

本系统的设计目标主要包括以下三个方面。

1. 将前面完成的三维定位跟踪算法从上位机仿真环境迁移到 FPGA 开发板 PS 端，使其能够在板载 Linux 系统中独立执行。
2. 设计轻量化的人机交互界面，使实验参数配置、算法运行和结果查看均可在开发板本地完成，便于现场演示和实验记录。
3. 在保证系统资源占用较低的前提下，实现轨迹图、误差指标和运行时间等核心信息的可视化显示，为后续板端验证和论文截图提供支撑。

围绕上述目标，系统采用分层实现思路。底层为定位跟踪算法核心层，负责状态预测、测量建模和滤波更新；中间层为实验封装层，负责场景组织、测量数据生成、实验流程控制和结果统计；上层为板端显示与交互层，负责参数配置、页面绘制、键盘输入响应和结果展示。通过这种结构划分，算法本身与界面显示彼此解耦，既便于后续修改显示方式，也便于将算法部分继续移植到命令行程序、网络服务程序或后续的射频实测链路中。

需要说明的是，程序底层已经预留了多种测量体制和多目标扩展能力，但第五章论文实验仍以单目标模式为主，重点使用 TDOA 与 AOA 两种测量量开展验证。因此，本节在描述系统实现时既说明通用软件架构，也突出单目标板端实验链路这一核心任务。

## 5.4.2 PC 端交叉编译与板端部署流程

### 1. 采用交叉编译的原因

在算法完成 C 语言实现之后，还需要解决“如何让程序真正运行到开发板上”的问题。根据前期调试结果可知，开发板当前的 PetaLinux 系统中未预装完整的本地编译环境，板端无法直接使用 `gcc` 对源代码进行编译；同时，如果在其他 Linux 环境中生成普通的动态链接可执行文件，再复制到开发板运行，还可能出现目标板 `glibc` 版本不匹配的问题。因此，本文没有采用“板端本地编译”的方式，而是选择在 Windows 主机上完成 ARM 交叉编译，再将生成的可执行文件复制到开发板运行。

这种方式具有两点优势。一方面，PC 端计算资源更充足，编译环境更容易统一管理；另一方面，通过交叉编译脚本可以明确指定目标处理器架构、硬件浮点方式和链接策略，从而保证生成的程序能够稳定运行在 Zynq PS 端 Cortex-A9 处理器上。为进一步提高兼容性，本课题在交叉编译阶段采用了静态链接方式，从而减少板端运行时对系统动态库版本的依赖，提高了程序的可部署性。

### 2. Windows 端交叉编译实现

本文在工程目录中编写了 `build_cross_arm.ps1` 脚本，用于在 Windows PowerShell 环境下调用 ARM GNU Toolchain 完成交叉编译。该脚本首先自动检查交叉编译器是否可用，然后针对 Zynq PS 端 Cortex-A9 架构设置编译选项，包括硬件浮点支持、优化等级和静态链接选项，最后分别生成命令行实验程序 `tracker_demo` 与 LCD 界面程序 `fb_tracker_ui`。

Windows 端的典型操作流程如下：

```powershell
$env:CROSS_PREFIX = "D:\Program Files (x86)\Arm\GNU Toolchain mingw-w64-i686-arm-none-linux-gnueabihf\bin\arm-none-linux-gnueabihf-"
cd C:\Users\xaq\Desktop\Graduation_Project\chapter5\ps_tracker
.\build_cross_arm.ps1
```

执行完成后，程序会在 `build_arm` 目录下生成以下 ARM 可执行文件：

1. `tracker_demo`，用于命令行方式运行单目标或多目标跟踪实验。
2. `fb_tracker_ui`，用于在 framebuffer 显示屏上运行交互界面。

这一步实际上完成了“将 PC 端源代码转换为板端 ARM 可执行程序”的过程，是算法移植落地到开发板的关键工程环节。如果只描述算法和显示界面，而不说明这一交叉编译过程，那么“PS 端移植”这一结论是不完整的。

### 3. 部署文件打包与复制

为了便于上板部署，工程中进一步编写了 `stage_for_usb.ps1` 脚本。该脚本会在 `stage_usb` 目录下集中整理需要复制到开发板的文件，包括：

1. `tracker_demo`
2. `fb_tracker_ui`
3. `board_probe.sh`
4. `run_cli_tests.sh`
5. `run_linux_fb.sh`
6. `DEPLOY_LINUX_FB.md`

对应的打包命令如下：

```powershell
.\stage_for_usb.ps1
```

完成后，即可将 `stage_usb` 目录中的内容复制到 U 盘或 SD 卡启动分区，再插入开发板进行部署。结合本课题实际调试过程，推荐优先将可执行文件复制到 SD 卡启动分区 `/media/sd-mmcblk0p1` 中运行。其原因在于：一是根文件系统在某些情况下可能被重新挂载为只读，导致无法覆盖旧程序；二是个别 U 盘在板端可能出现 FAT 文件系统读写异常。相比之下，SD 启动分区更加稳定，也更便于在后续实验中直接替换新的二进制版本。

### 4. 板端运行与验证

将交叉编译所得文件复制到开发板后，用户即可在板端 Linux 中直接运行。典型流程如下：

```bash
cd /media/sd-mmcblk0p1
./tracker_demo --scene straight --tdoa --steps 80 --seed 1
./fb_tracker_ui
```

其中，前一条命令用于快速验证算法功能、误差指标和运行时间；后一条命令用于启动图形界面，并在显示屏上观察轨迹图和实验结果。通过这种“Windows 端编译，板端部署运行”的方式，最终形成了完整的软件落地链路，即源代码开发位于 PC 端，目标程序执行位于 FPGA PS 端，二者通过 ARM 交叉编译工具链衔接起来。

因此，从工程实现角度看，本课题的板端系统并不是在开发板上临时编写和编译出来的，而是经历了“PC 端交叉编译 -> 部署文件整理 -> 复制到开发板 -> 板端运行验证”这一完整过程。这一过程也是论文中说明算法工程化移植时不可缺少的内容。

## 5.4.3 PS 端算法移植方案

### 1. 状态模型移植

在算法移植过程中，首先需要将 MATLAB 中较为灵活的矩阵运算流程转化为适合嵌入式平台执行的 C 语言实现。本文在 PS 端采用六维状态向量描述目标运动状态，即

```text
xk = [px, py, pz, vx, vy, vz]^T
```

其中，`px、py、pz` 表示目标三维位置，`vx、vy、vz` 表示三维速度。预测阶段采用离散常速度模型完成状态外推，即在相邻采样周期内利用速度对位置进行更新，同时结合过程噪声协方差完成状态不确定性的传播。该部分在 `tracker3d.c` 中由 `tracker3d_predict()` 完成，其作用是根据当前状态和采样周期 `dt` 先得到先验估计，再为后续测量更新提供预测基础。

### 2. 测量模型移植

为了使同一套框架能够支持不同定位体制，本文在 PS 端保留了 TDOA、TOA、AOA 和 RSS 四类测量模型。其物理含义如下。

1. `TDOA` 表示目标到某一锚点与参考锚点之间的传播时间差，对应距离差观测。
2. `TOA` 表示目标到各锚点的绝对传播时间，对应绝对距离观测。
3. `AOA` 表示目标相对锚点的到达角信息，在程序中进一步拆分为方位角和俯仰角两部分。
4. `RSS` 表示接收信号强度，通过路径损耗模型间接反映目标与锚点之间的距离关系。

在具体实现中，程序并没有为每一种组合情况分别编写独立滤波器，而是采用统一测量描述符机制动态组织测量向量。`tracker3d.c` 中首先根据当前配置判断哪些观测量有效，然后按顺序构造测量向量、预测量、雅可比矩阵以及测量噪声方差。这样做有两个好处：一是代码结构统一，便于维护；二是当实验只启用某一种测量体制时，滤波器会自动生成对应维度的观测模型，无需额外改写算法主体。也正因为如此，后续在界面中切换 `TDOA`、`AOA` 等模式时，底层算法可以直接复用同一套状态更新框架。

### 3. 递推滤波实现

在测量更新阶段，程序采用扩展卡尔曼滤波思想对非线性测量方程进行一阶线性化处理。对于每一帧数据，算法先根据预测状态计算理论测量值，再构造观测雅可比矩阵，随后结合卡尔曼增益完成状态校正与协方差更新。相关流程在 `tracker3d_update()` 中实现，而 `tracker3d_step()` 则将“预测 + 更新”封装为单步递推接口。这样一来，上层程序只需在每个时刻提供当前测量和采样周期，即可持续获得目标状态估计结果。

### 4. 板端测量仿真

由于当前阶段论文实验主要验证的是 PS 端算法移植与显示系统，而非真实射频链路闭环，因此程序在板端同时实现了测量仿真功能。`tracker3d_simulate_measurement()` 可根据目标真值状态、锚点分布和噪声参数直接生成带噪测量量。这样就将原本需要在 MATLAB 中完成的“真值生成 + 测量生成”环节也一起迁移到了开发板端，使 PS 端能够独立完成整套实验流程。对毕业设计而言，这一步非常关键，因为它表明系统已具备脱离上位机、在板端自洽运行的能力。

## 5.4.4 跟踪算法软件架构实现

为了保证系统清晰、可维护，并方便后续对接实测数据，本文将 PS 端软件划分为三个层次。

### 1. 算法核心层

算法核心层对应 `tracker3d.c`，主要负责以下功能：

1. 定义状态维数、测量结构体和配置结构体。
2. 实现状态预测、测量更新和单步递推。
3. 建立 TDOA、TOA、AOA、RSS 的观测模型。
4. 根据当前启用的测量体制自动计算测量维数。
5. 生成带噪声的仿真测量值。

这一层是整个系统最底层的数学求解引擎，其特点是只关心“输入什么测量、输出什么状态”，并不关心这些测量来自命令行、LCD 界面还是未来的射频采样链路。因此，它具有较强的复用性。

### 2. 实验封装层

实验封装层对应 `tracker_app.c`，位于算法核心层与界面层之间，承担“组织一次完整实验”的职责。该层主要完成以下工作：

1. 配置锚点位置和参考锚点编号，当前示例程序使用 5 个锚点组成三维观测网络。
2. 定义 `straight`、`turn`、`climb` 三种典型目标运动场景。
3. 提供 `single` 与 `multi3` 两类目标模式，其中论文实验主要使用 `single`。
4. 根据用户选择的测量模式，自动启用对应测量体制。
5. 在每个采样时刻生成目标真值轨迹、测量数据并调用底层滤波器递推。
6. 保存整段实验中的真值历史和估计历史。
7. 计算位置均方根误差、速度均方根误差、总运行时间和平均单步耗时。

这一层的作用可以理解为“实验控制器”。如果没有它，界面程序就必须直接操作底层滤波器，既不利于管理，也不利于后续复用。通过 `tracker_run_simulation()` 这一统一入口，无论是命令行程序 `tracker_demo`，还是 LCD 界面程序 `fb_tracker_ui`，都可以调用同一套实验逻辑，从而保证两种运行方式下算法行为一致、结果统计口径一致。

### 3. 显示与交互层

显示与交互层对应 `fb_linux_main.c`。这一层并不直接关心滤波算法内部细节，而是更关注“用户如何配置实验”和“结果如何呈现在屏幕上”。它主要完成参数菜单显示、按键处理、页面切换、图形绘制以及结果页面刷新等任务。通过将这一层与算法层分离，系统实现了较好的模块解耦：即使后续将 LCD 界面替换为串口菜单、网页界面或 Qt 图形界面，底层实验代码依旧可以保持不变。

## 5.4.5 板端显示系统实现

### 1. 基于 Linux framebuffer 的轻量化显示方案

考虑到开发板 PS 端资源有限，同时本课题的目标是完成实验验证而非构建复杂桌面软件，因此本文没有采用 Qt、X11 等重量级图形框架，而是直接基于 Linux framebuffer 实现板端显示。程序启动后首先打开 `/dev/fb0` 设备文件，通过 `ioctl` 读取屏幕分辨率、像素位宽和行跨度等参数，再利用 `mmap` 将显存映射到用户空间。这样，程序便可直接向显示缓冲区写入像素数据，实现最直接、最轻量的图形输出。

为了减小直接写显存造成的闪烁现象，程序在内存中额外申请了一个后备缓冲区 `backbuffer`。每一帧界面绘制时，先在后备缓冲区中完成矩形、文字、曲线和边框的绘制，随后再一次性刷新到真实 framebuffer。该方法相当于简化版的双缓冲机制，既保持了实现简单，又能满足本实验界面的稳定显示需求。

### 2. 页面组织方式

界面整体采用双页面结构，包括主菜单页和结果显示页。

1. 主菜单页用于设置实验参数。
2. 结果显示页用于展示本次实验的数值指标和轨迹图。

其中，主菜单页包含 `SCENE`、`TARGETS`、`MODALITY`、`STEPS`、`SEED`、`RUN`、`QUIT` 等项目。用户可以通过这些菜单项完成实验场景、目标模式、测量体制、仿真步数和随机种子的配置。程序还会根据当前测量体制动态计算测量维数，并在界面上实时显示，便于用户了解当前实验的数据规模。

结果页则集中显示 `SCENE`、`TARGETS`、`MODALITY`、`STEPS`、`DIM`、`POS RMSE`、`VEL RMSE`、`TOTAL` 和 `STEP` 等信息。其中，`TOTAL` 表示本次实验的总运行时间，`STEP` 表示平均每一步的处理时间。这些指标可以直接反映 PS 端算法执行的实时性水平，也是板端移植是否成功的重要依据。

### 3. 基础绘图功能实现

界面绘图的基础能力由 `ui_draw.c` 提供，包括像素绘制、矩形填充、边框绘制、线段绘制和简单文本绘制等。上层页面程序不再直接操作每个像素，而是通过这些基础接口构建菜单和图形区域。这样既简化了页面逻辑，也使得显示代码更清晰。

由于 LCD 分辨率有限，界面在布局时采取了“上部信息栏 + 下部图形区”的方式。主菜单页重点保证参数列表清晰可读；结果页则优先保证误差数据和轨迹图同时可见，使用户无需切换页面即可观察数值结果与运动轨迹之间的对应关系。

## 5.4.6 参数配置与交互流程实现

当前实验平台尚未引入触摸屏，因此系统采用串口终端按键作为输入方式。程序通过 `termios` 将标准输入设置为非规范模式，并关闭回显功能，从而实现按键的即时响应；同时结合 `select` 机制对标准输入进行非阻塞检测，使界面程序能够在持续刷新的同时及时读取用户操作，而不会因等待按键而阻塞界面显示。

当前按键定义如下：

1. `W/S` 用于上下切换当前选中的菜单项。
2. `A/D` 用于修改当前菜单项对应的参数值。
3. `Enter` 用于确认当前操作，在选中 `RUN` 时启动实验。
4. `M` 用于在结果页返回主菜单。
5. `R` 用于在结果页按照当前参数直接重新运行实验。
6. `Q` 用于退出程序。

基于上述设计，板端实验的执行流程可概括为以下步骤。

1. 启动 `fb_tracker_ui`，系统进入主菜单页。
2. 用户通过串口按键设置场景、目标模式、测量模式、步数和随机种子。
3. 用户选择 `RUN` 后，界面层调用实验封装层入口函数。
4. 实验封装层完成真值轨迹生成、测量生成、滤波递推和误差统计。
5. 结果页显示误差指标、运行时间和轨迹图。
6. 用户可返回主菜单修改参数，或直接重复运行当前实验。

这样，原本需要在 PC 端分多步完成的实验流程，在开发板上被统一组织为一套闭环交互系统。对于现场答辩或展示而言，操作者只需连接串口和显示屏即可完成实验，不再需要频繁切换多个软件环境。

## 5.4.7 轨迹显示与三维可视化实现

### 1. 二维投影视图

为了直观展示估计轨迹与真实轨迹之间的差异，结果页绘制了 `XY VIEW` 和 `XZ VIEW` 两幅投影图。前者主要观察目标在水平面内的运动变化，后者主要观察目标高度方向的变化趋势。程序在绘图前会遍历整段历史轨迹，自动计算坐标范围并完成归一化缩放，从而保证不同场景下的轨迹都能完整显示在固定大小的绘图区域中。浅色曲线表示真实轨迹，深色曲线表示估计轨迹，用户可以直接通过两条曲线之间的偏差判断跟踪精度。

### 2. 三维运动趋势显示

除了二维投影外，程序还设计了 `3D VIEW` 区域，用于展示目标在三维空间中的整体运动趋势。需要指出的是，这里并没有引入 OpenGL 等三维图形库，而是采用固定视角的等轴测投影方法，将三维坐标映射到二维 LCD 平面。其本质思想是先根据目标的 `(x, y, z)` 坐标计算投影坐标 `(x', y')`，再按照普通二维折线图方式绘制。这样虽然不是严格意义上的可旋转三维场景，但已经能够较为直观地体现目标在空间中的上升、转向和位移变化。

这一设计非常适合当前平台。一方面，它避免了复杂图形库对处理器资源和软件环境的额外要求；另一方面，又比单纯的二维平面图更能体现“三维跟踪”的实验特征。因此，从工程实现和展示效果两方面看，固定视角三维投影是一种资源开销较低且效果较好的折中方案。

### 3. 结果页信息组织

结果页除了图形之外，还同步显示误差和时间统计信息。这样设计的原因在于：如果只显示 RMSE 数值，用户很难直观看到估计轨迹与真实轨迹在局部区域的偏差；如果只显示轨迹图，又难以用统一指标比较不同参数配置下的算法效果。因此，本文将“数值指标 + 图形结果”统一放在同一页面中，以提高实验分析效率。

## 5.4.8 系统特点与实现效果分析

综合来看，本文实现的 PS 端算法移植显示系统具有以下特点。

1. 轻量化。系统直接面向 framebuffer 进行绘制，不依赖复杂图形框架，适合资源受限的嵌入式 Linux 平台。
2. 可独立运行。目标轨迹生成、测量仿真、状态估计和结果显示均在开发板本地完成，摆脱了对 MATLAB 在线运行的依赖。
3. 分层清晰。算法核心层、实验封装层和显示层彼此解耦，后续便于维护、调试和扩展。
4. 具备明确的工程部署路径。系统先在 Windows 主机完成 ARM 交叉编译，再通过 SD 卡或 U 盘复制到开发板运行，形成了完整的软件移植链路。
5. 具备扩展基础。当前系统已经形成统一实验入口，后续既可以继续扩展多目标场景，也可以将仿真测量替换为真实射频采样数据，实现从“板端仿真验证”向“板端实测验证”的平滑过渡。

结合前面的板端实验过程可以看出，该系统已经能够稳定完成参数配置、算法运行、轨迹显示和误差统计等任务，证明三维定位跟踪算法已经成功迁移至 FPGA PS 端，并可在实际开发板环境中完成独立运行和可视化展示。这为第五章后续实验结果分析提供了可靠的平台基础。

## 5.4.9 本节小结

本节围绕第五章的板端实验需求，完成了交互界面与 PS 端算法移植显示系统的设计与实现。本文先在 Windows 主机上通过 ARM 交叉编译工具链生成适用于 Zynq PS 端的可执行程序，再将二进制文件部署到开发板中运行；随后在板端 Linux 用户态下完成目标轨迹仿真、测量生成、状态估计、误差统计和 framebuffer 图形显示。通过这一实现过程，系统最终具备了“PC 端开发编译、PS 端本地运行、LCD 本地显示”的完整能力，为后续单目标 TDOA/AOA 实验验证提供了直接支撑，也为进一步接入真实射频数据奠定了软件架构基础。
