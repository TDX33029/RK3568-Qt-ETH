## 5.1 引言

前文已经围绕微弱目标跟踪问题，分别完成了定位测量建模、状态估计方法设计以及软件原型验证。然而，算法在 MATLAB 或 PC 环境中的仿真结果只能说明理论方案具备可行性，并不能直接证明其在嵌入式平台上的可部署性与可运行性。对于面向工程实现的目标跟踪系统而言，还需要进一步验证算法能否在资源受限的嵌入式处理器上稳定执行，实验数据能否脱离上位机环境在板端自主生成与处理，以及系统是否具备良好的可配置性、可显示性和可演示性。

基于上述考虑，本章以 AC820 Zynq 开发板为硬件平台，围绕“单目标三维定位跟踪算法在 PS 端实现并完成板端显示验证”这一目标，设计并实现了一套嵌入式实验验证系统。该系统以 Zynq-7020 的 PS 端为核心计算平台，在 Linux 用户态下运行三维定位跟踪算法，通过 SD 卡完成系统启动与程序部署，并利用 LCD 显示屏和串口终端构建轻量化的人机交互环境。与传统“上位机离线仿真、串口输出数值”的验证方式不同，本文实现的系统能够在开发板端自主完成目标轨迹仿真、测量量生成、状态估计、误差统计以及结果显示，从而形成“PC 端开发编译、板端本地运行、板端本地显示”的完整验证链路。

需要说明的是，当前板端工程底层保留了 `TDOA`、`TOA`、`AOA` 和 `RSS` 四类测量模式，并支持固定三目标演示功能，但结合论文主体内容与实验重点，本章正文主要围绕单目标场景下的 `TDOA` 与 `AOA` 两种测量模式展开分析。这样既能够与前文算法研究内容保持一致，也能够突出第五章在工程移植与嵌入式验证方面的核心贡献。

本章首先介绍硬件平台和系统整体架构，随后说明算法从 MATLAB/PC 环境向 PS 端 C 语言程序的移植过程，在此基础上阐述基于 Linux framebuffer 的交互界面与显示系统设计，最后给出单目标场景下的板端实验结果，并对定位精度和运行时间进行分析。

## 5.2 硬件平台与系统架构

### 5.2.1 AC820 开发板及外围实验平台

本课题的嵌入式验证平台选用 AC820 Zynq 开发板。该开发板以 Xilinx Zynq-7020 SoC 为核心器件，片上同时集成处理系统（Processing System，PS）与可编程逻辑（Programmable Logic，PL）两部分。其中，PS 端包含双核 ARM Cortex-A9 处理器，可运行嵌入式 Linux 系统并承担算法计算任务；PL 端则提供可编程逻辑资源，用于支持板级外设扩展和后续功能扩展。相较于纯 MCU 平台，Zynq 结构能够兼顾嵌入式软件开发的灵活性和可编程硬件平台的可扩展性，因而适合作为算法验证和系统实现的基础平台。

结合本章实验需求，实际使用的外围设备主要包括 SD 启动卡、LCD 显示屏、串口调试连接以及电源模块。SD 卡用于存放启动镜像、Linux 内核和板端可执行程序；LCD 用于显示菜单界面、结果信息和轨迹图；串口终端用于观察启动日志、登录 Linux 系统并输入控制按键。需要强调的是，本章并未将定位跟踪算法放入 PL 中实现，而是将状态预测、测量更新、误差统计和界面控制逻辑统一部署在 PS 端完成，从而重点验证“单目标三维定位跟踪算法在 PS 端运行”的目标。

### 5.2.2 系统整体架构

为保证算法验证流程完整且便于调试，本文构建了由 Windows 主机、SD 启动介质、Zynq 开发板、LCD 显示屏以及串口终端组成的实验系统。整个系统的工作流程可以概括为：首先在 Windows 主机端完成源代码编写、交叉编译和上板文件整理；随后将生成的 ARM 可执行程序复制到 SD 卡启动分区并插入开发板；开发板从 SD 卡启动 Linux 系统后，在 PS 端运行 `tracker_demo` 或 `fb_tracker_ui`；最后通过串口完成参数输入，并通过 LCD 实时显示实验结果。

从功能分配上看，系统中的 PS 端承担了算法运行和显示控制两类核心任务。一方面，在实验过程中由 PS 端自主生成目标真值轨迹和测量量，并执行定位跟踪递推计算；另一方面，在实验完成后由 PS 端将误差指标、运行时间以及轨迹图绘制到 LCD 上显示。PL 端在当前章节中不承担定位跟踪算法计算任务，而是作为板级系统资源的一部分，为 Linux 启动环境和外设显示链路提供基础支撑。基于这样的结构设计，本文最终实现了从“PC 端开发编译”到“板端算法运行”再到“板端结果显示”的完整闭环，明显提升了实验验证的独立性和工程展示能力。

### 5.2.3 启动镜像制作与 Linux 系统搭建

为使板端程序能够稳定运行，本章首先完成了 SD 卡启动系统的制作与 Linux 运行环境搭建。启动介质采用典型的双分区方式：第一分区为 FAT 格式启动分区，用于存放 `BOOT.BIN`、`zImage`、`system.dtb` 和 `boot.scr` 等文件；第二分区为 ext4 根文件系统分区，用于挂载 Linux 运行环境。系统启动时，开发板首先从 SD 卡读取引导文件，随后完成内核加载、设备树解析以及根文件系统挂载，最终进入 Linux 登录界面。

在实际调试过程中，通过串口终端观察启动日志并成功登录系统，确认了以下关键条件均已满足：Linux 系统能够从 SD 卡正常启动，网络、存储和串口等基础外设能够被系统识别，framebuffer 设备 `/dev/fb0` 正常存在并可用于后续 LCD 图形界面显示，系统中同时存在基础输入设备节点，可配合串口输入完成人机交互。进一步探测结果表明，当前 framebuffer 工作于 `800 × 480` 分辨率、16 位色深模式，这为后续界面布局和轨迹图绘制提供了明确的显示约束条件。

与直接在板端临时编译程序相比，先构建稳定的 Linux 运行环境再部署算法程序的方式更加适合毕业设计实验。一方面，Linux 用户态程序开发和调试更灵活；另一方面，后续若需要接入文件系统、网络通信或外部采样数据，也可以在现有系统基础上继续扩展。

## 5.3 算法移植与实现

### 5.3.1 算法移植目标与总体思路

第五章的核心任务并不是重新设计新的定位跟踪算法，而是将前文完成的单目标三维定位跟踪方法迁移到嵌入式平台，使其能够在 PS 端独立稳定运行。为此，本文在移植过程中坚持以下思路：首先保持算法功能完整，确保板端程序保留状态预测、测量更新、误差统计和场景切换等核心能力；其次尽量降低对 MATLAB 的依赖，使目标轨迹和测量量均由板端程序自主仿真生成；再次通过模块化方式提升工程可维护性，将算法核心、实验封装和显示逻辑彼此分离；最后在论文正文中聚焦单目标 `TDOA` 与 `AOA` 两种测量模式，以保证实验内容与全文主线保持一致。

基于上述思路，本文最终实现的板端程序既能够用于命令行方式快速验证算法，也能够用于 LCD 图形界面展示，从而兼顾调试效率与展示效果。

### 5.3.2 C 语言化的状态与测量模型

为适应嵌入式平台开发需求，本文将原有算法逻辑重构为 C 语言程序。目标状态向量采用六维形式表示为

$$
\mathbf{x}_k = [p_{x,k},\, p_{y,k},\, p_{z,k},\, v_{x,k},\, v_{y,k},\, v_{z,k}]^T
$$

其中，$p_{x,k}$、$p_{y,k}$、$p_{z,k}$ 分别表示三维位置分量，$v_{x,k}$、$v_{y,k}$、$v_{z,k}$ 分别表示三维速度分量。状态预测阶段采用离散恒速模型完成外推，并通过过程噪声协方差反映模型不确定性；测量更新阶段则采用扩展卡尔曼滤波思想，对非线性测量方程进行一阶线性化处理，进而完成状态校正。

在测量模型方面，板端程序支持 `TDOA`、`TOA`、`AOA` 和 `RSS` 四类观测方式。其中，`TDOA` 代表相对传播时间差量测，`TOA` 代表绝对传播时间量测，`AOA` 由方位角和俯仰角两部分构成，`RSS` 则通过路径损耗模型反映目标与锚点之间的距离关系。为了保证程序结构统一，系统采用动态测量组织方式，即根据当前用户选择的测量模式自动生成相应维度的测量向量和噪声方差矩阵，而不是为每种测量量单独编写一套滤波器。

需要强调的是，论文实验中每次只启用一种测量量，即单次实验仅在 `TDOA` 与 `AOA` 等模式中选择其一，而不采用多测量量混合更新的方式。这样做有助于更清晰地比较不同测量体制对跟踪性能的影响，同时也与第五章“单目标情况下不同测量模式的板端实现与验证”这一实验目标保持一致。

### 5.3.3 场景、参数与实验流程管理

为避免板端实验仍依赖 MATLAB 生成输入数据，本文在 PS 端程序中实现了完整的场景管理与自主仿真流程。系统预置了三种典型目标运动场景，即 `straight`、`turn` 和 `climb`，分别对应直线运动、平面转向机动和包含明显高度变化的运动情形。对于每一类场景，程序都能够在板端自动生成目标真值轨迹，并根据当前启用的测量模式产生带噪测量量，随后调用滤波器递推完成状态估计。与此同时，程序还负责保存整段实验过程中的真值历史和估计历史，并在实验结束后计算位置均方根误差、速度均方根误差、总运行时间以及平均单步耗时等指标。

从软件结构上看，板端工程可以划分为算法核心模块、实验封装模块和显示交互模块三个层次。算法核心模块负责状态预测、观测建模和滤波更新；实验封装模块负责场景生成、参数管理和结果统计；显示交互模块负责参数选择、界面绘制和页面切换。这种分层实现方式使得命令行程序和图形界面程序可以共享同一套实验逻辑，从而保证不同运行入口下的算法行为一致。

### 5.3.4 Windows 交叉编译与板端部署

在完成 C 语言程序实现之后，还需要解决“如何将程序真正部署到开发板运行”的问题。由于当前板端 Linux 系统中未配置完整的本地编译环境，无法直接使用 `gcc` 编译源代码；同时，普通动态链接程序在跨系统运行时可能出现 `glibc` 版本不匹配问题。因此，本文采用 Windows 主机端交叉编译的方式生成适用于 Zynq PS 端的 ARM 可执行文件。

具体而言，工程中编写了 `build_cross_arm.ps1` 脚本，调用 ARM GNU Toolchain 对命令行程序 `tracker_demo` 和图形界面程序 `fb_tracker_ui` 进行交叉编译，并通过静态链接方式提高目标板运行兼容性。其后，利用 `stage_for_usb.ps1` 脚本将上板所需文件统一整理到 `stage_usb` 目录中，再复制到 SD 卡启动分区。结合实际调试经验，本文最终选择从 `/media/sd-mmcblk0p1` 直接运行新版程序，以避免根文件系统只读和 U 盘读写异常等问题。

这一过程表明，本章所实现的板端系统并非在开发板上临时编写和编译生成，而是完整经历了“PC 端源代码开发、Windows 主机交叉编译、SD 卡部署以及板端运行验证”的工程化流程。该流程也是毕业设计中“算法从仿真走向嵌入式实现”的重要体现。

## 5.4 交互界面设计与显示实现

### 5.4.1 基于 framebuffer 的轻量化显示方案

考虑到嵌入式平台资源有限，同时本课题的目标是完成实验验证而非构建复杂桌面软件，因此本文没有引入 Qt、X11 等重量级图形框架，而是直接基于 Linux framebuffer 实现板端图形显示。程序启动后，首先打开 `/dev/fb0` 设备文件，读取屏幕分辨率、像素位宽和行跨度等参数，再通过内存映射方式访问显存区域。随后，程序在内存中建立后备缓冲区，先完成各类图形元素绘制，再统一刷新到显示设备，从而有效减小直接写显存带来的闪烁现象。

这一设计具有较强的工程适应性。其一，实现路径简单，便于在嵌入式 Linux 环境中快速部署；其二，不依赖复杂第三方图形库，降低了软件体积和运行负担；其三，能够满足当前实验系统对菜单显示、文字显示和二维轨迹绘图的实际需求。对于毕业设计的板端验证任务而言，framebuffer 方案在实现复杂度和显示效果之间取得了较好的平衡。

### 5.4.2 界面组织与交互逻辑

板端界面整体采用双页面结构，包括主菜单页和结果显示页。主菜单页主要用于实验参数配置，结果显示页则用于显示本次实验的误差指标和轨迹图。菜单页中可配置的参数包括运动场景 `SCENE`、目标模式 `TARGETS`、测量模式 `MODALITY`、仿真步数 `STEPS`、随机种子 `SEED` 以及运行入口 `RUN` 和退出入口 `QUIT`。程序还会根据当前测量模式自动计算每帧测量维数，并在界面中给出显示，便于用户了解当前实验的数据规模。

由于当前实验平台未接入触摸屏，本章采用串口终端按键作为交互输入方式。具体而言，`W/S` 用于在菜单中上下移动，`A/D` 用于切换当前选项的参数值，`Enter` 用于执行运行操作，`M` 用于在结果页返回菜单，`R` 用于按当前参数重新运行实验，`Q` 用于退出程序。通过这种设计，用户无需借助鼠标或键盘外设，仅通过串口终端即可完成实验配置与触发，操作方式简单直接，较为适合开发板环境下的实验演示。

### 5.4.3 轨迹绘制与三维可视化

为便于直观观察板端跟踪结果，结果页同时绘制了 `XY VIEW`、`XZ VIEW` 和 `3D VIEW` 三个视图。其中，`XY VIEW` 用于显示目标在水平平面上的运动轨迹，`XZ VIEW` 用于显示目标高度方向的变化情况，而 `3D VIEW` 则采用固定视角的等轴测投影方式，将三维轨迹映射到二维显示平面中。虽然这种方式并非完整的三维图形渲染，但能够在不引入复杂图形库的前提下有效表现目标在空间中的运动趋势。

在绘图实现上，程序首先遍历全段真值轨迹与估计轨迹，自动计算坐标范围并进行归一化缩放，然后使用折线方式分别绘制真实轨迹和估计轨迹。结果页中还会同步显示位置 RMSE、速度 RMSE、总运行时间和平均单步耗时等指标。

## 5.5 实验结果与分析

### 5.5.1 实验方案与评价指标

为验证所设计的单目标三维定位跟踪算法在开发板 PS 端的可行性与有效性，本文将交叉编译生成的 `tracker_demo` 和 `fb_tracker_ui` 部署到 Zynq/AC820 开发板 Linux 系统中运行。实验过程中，目标运动轨迹和测量数据均由 PS 端程序自主仿真生成，不依赖 MATLAB 离线生成输入文件；状态估计算法在板端独立完成预测、更新和误差统计。

结合论文主体内容与实验重点，本文在实验部分选取 `TDOA` 和 `AOA` 两种代表性测量模式进行对比分析。其中，`TDOA` 可代表基于时间差测量的定位方式，`AOA` 可代表基于空间角度约束的定位方式。两者分别从“低维时间测量”和“高维角度测量”两个角度反映三维定位性能差异。实验场景设置为 `straight`、`turn` 和 `climb` 三类典型运动方式，以覆盖直线运动、转向机动和高度变化三种情况。实验过程中统一采用单目标模式，采样周期设置为 0.1 s，随机种子固定为 1，其中 `straight` 场景步数为 80，`turn` 场景和 `climb` 场景步数均为 60。评价指标采用位置均方根误差 `Position RMSE`、速度均方根误差 `Velocity RMSE`、总运行时间 `Total runtime` 和单步平均运行时间 `Average step time`。

表 5-2 给出了单目标实验的基本参数设置。

**表 5-2 单目标实验参数设置**

| 参数 | 取值 |
| --- | --- |
| 目标模式 | `single` |
| 测量模式 | `TDOA`、`AOA` |
| 采样周期 | 0.1 s |
| 随机种子 | 1 |
| `straight` 场景步数 | 80 |
| `turn` 场景步数 | 60 |

### 5.5.2 定位精度结果分析

表 5-3 汇总了三种运动场景下两种测量模式对应的定位精度结果。可以看到，在所有实验场景中，AOA 模式均表现出更优的定位与测速性能，而 TDOA 模式则体现出较低维度条件下仍然可接受的工程可用性。

**表 5-3 三种场景下的定位精度对比**

| 场景 | 测量模式 | 测量维数/帧 | 位置 RMSE/m | 速度 RMSE/(m/s) |
| --- | --- | ---: | ---: | ---: |
| `straight` | TDOA | 4 | 0.1892 | 0.2160 |
| `straight` | AOA | 10 | 0.0770 | 0.1571 |
| `turn` | TDOA | 4 | 0.1986 | 0.2181 |
| `turn` | AOA | 10 | 0.0922 | 0.1796 |
| `climb` | TDOA | 4 | 0.1955 | 0.2095 |
| `climb` | AOA | 10 | 0.0926 | 0.1871 |

在 `straight` 场景下，AOA 模式的位置 RMSE 为 0.0770 m，仅约为 TDOA 模式的 40.7%，说明角度信息对目标三维位置具有更强的几何约束能力。在 `turn` 场景下，目标运动状态变化更复杂，两种模式的误差均较直线场景略有增加，但 AOA 仍保持明显优势，其位置 RMSE 为 0.0922 m，较 TDOA 降低约 53.6%，表明在存在机动的情况下，角度测量对状态变化具有更好的适应能力。在 `climb` 场景下，目标存在明显高度变化，能够同时提供方位角和俯仰角信息的 AOA 模式优势进一步体现，其位置 RMSE 为 0.0926 m，而 TDOA 模式则为 0.1955 m。

进一步对三类场景结果进行平均，可以得到 TDOA 模式的平均位置 RMSE 为 0.1944 m，平均速度 RMSE 为 0.2145 m/s；AOA 模式的平均位置 RMSE 为 0.0873 m，平均速度 RMSE 为 0.1746 m/s。由此可见，AOA 在三种场景下均取得了更优的定位效果，且精度波动较小，表现出较好的稳定性。TDOA 虽然精度略低，但误差整体仍控制在 0.2 m 量级以内，说明其仍具备一定的工程应用价值。从实验结果来看，TDOA 更适合作为低维、低复杂度的基线方案，而 AOA 则更适合作为追求较高定位精度时的优选方案。

### 5.5.3 运行时间分析

在完成定位精度验证后，还需要进一步分析算法在开发板 PS 端的运行效率，以评估其实时处理能力。表 5-4 给出了三种场景下两种测量模式的运行时间统计结果。

**表 5-4 各场景运行时间统计结果**

| 场景 | 测量模式 | 总耗时/ms | 单步耗时/ms |
| --- | --- | ---: | ---: |
| `straight` | TDOA | 4.387 | 0.055 |
| `straight` | AOA | 10.110 | 0.126 |
| `turn` | TDOA | 3.265 | 0.054 |
| `turn` | AOA | 7.638 | 0.127 |
| `climb` | TDOA | 3.266 | 0.054 |
| `climb` | AOA | 7.645 | 0.127 |

由表 5-4 可以看出，AOA 的总耗时和单步耗时均高于 TDOA。这是因为 AOA 每帧测量维数更高，更新时涉及的测量建模和矩阵运算更多，因此其计算开销相应增加。为了进一步直观比较两种模式在精度和复杂度之间的权衡关系，表 5-5 给出了三类场景下的平均性能统计结果。

**表 5-5 两种模式的平均精度与平均耗时对比**

| 测量模式 | 平均位置 RMSE/m | 平均速度 RMSE/(m/s) | 平均总耗时/ms | 平均单步耗时/ms |
| --- | ---: | ---: | ---: | ---: |
| TDOA | 0.1944 | 0.2145 | 3.639 | 0.054 |
| AOA | 0.0873 | 0.1746 | 8.464 | 0.127 |

本实验采样周期为 0.1 s，即 100 ms。由表 5-5 可知，TDOA 模式的平均单步耗时仅为 0.054 ms，约占采样周期的 0.054%；AOA 模式的平均单步耗时为 0.127 ms，约占采样周期的 0.127%。即使是耗时更高的 AOA 模式，其单步计算时间也远小于 100 ms 的采样周期，仍然保留了较大的实时处理裕量。这说明所实现的单目标三维定位跟踪算法能够满足开发板 PS 端的实时运行需求。从“精度 - 复杂度”权衡角度分析，AOA 在获得更高定位精度的同时，付出了更高但仍然很小的计算开销；TDOA 虽然精度略逊，但单步耗时更低，更适合作为计算量较小的参考方案。

## 5.6 本章小结

本章围绕“单目标三维定位跟踪算法在 Zynq 平台 PS 端实现与验证”这一目标，完成了嵌入式实验系统的设计、部署和测试。首先，基于 AC820 Zynq 开发板构建了包含 SD 启动、Linux 运行环境、LCD 显示和串口交互的实验平台；随后，完成了算法从 MATLAB/PC 环境到 PS 端 C 语言程序的移植，并通过 Windows 主机交叉编译与 SD 卡部署方式实现了板端运行；在此基础上，进一步设计了基于 Linux framebuffer 的轻量化交互界面，使开发板能够在本地完成参数配置、算法运行和结果显示。

实验结果表明，所实现的板端程序能够稳定完成单目标三维定位跟踪任务。在三种典型运动场景下，AOA 模式的综合定位精度优于 TDOA 模式；与此同时，两种模式的单步耗时均远小于采样周期，表明算法在 PS 端具备良好的实时处理能力。综上，本文已经完成目标 1 中“单目标情况下的三维定位跟踪算法在 PS 端实现”的核心验证，并为后续系统扩展和实际外部数据接入奠定了平台基础。
